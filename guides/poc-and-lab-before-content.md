# PoC와 Lab — 콘텐츠보다 먼저, 수치는 사람이 화면에서 정한다

## 요약
새 게임(특히 새 차원·새 카메라)은 **PoC(되나?) → Lab(어떤 값이 좋나?) → Game(통과한 것만)** 순서로 시작한다. PoC는 통과 기준과 시간 상한이 있는 질문이고, Lab은 **게임 안의 화면**에서 수치를 바꾸고 바로 느끼고 프리셋으로 저장해 `tuning.rs`로 가져가는 도구다. 둘 다 콘텐츠(적 종류·방·이야기)를 쌓기 전에 한다. 첫 게임에서 "수치 한 곳 + 시나리오 진입점"까지는 했지만 "화면에서 바꾸기"가 없어 값 하나에 빌드 한 번이었다 — 두 번째 게임은 그 한 단을 더 올린다.

## 본문

### PoC — 질문·기준·상한
| 칸 | 내용 |
|---|---|
| 질문 | "이 스택으로 X가 되나?" 하나. 예: macroquad에서 쿼터뷰↔숄더뷰 전환이 튀지 않고 되나 |
| 통과 기준 | 눈으로 판정할 문장 2~4개 + 숫자 하나(프레임 시간, 드로콜 수). 판정은 사람이 |
| 시간 상한 | 날짜. 넘기면 **대안**(다른 엔진·다른 메커닉)으로 간다고 미리 적는다 |
| 산출물 | 결정 기록 하나(통과/실패/대안으로)와 시나리오 한 줄 |
- PoC 순서는 **가장 비싼 실패**부터: 엔진·플랫폼(렌더링·모델·패드) → 핵심 조작(카메라·이동) → 전투 → 콘텐츠.
- PoC 코드는 버려도 되지만 **경계**(입력 `Actions`, 수치 한 곳, 틱 고정)는 처음부터 지킨다. 그래야 통과한 PoC가 그대로 Game의 첫 줄이 된다.

### Lab — 게임 안의 튜닝 화면
- 실행 중에 값을 바꾸고 → 즉시 반영 → 프리셋 저장·비교 → `tuning.rs`에 붙여 넣을 텍스트로 내보내기. 커서 없이(패드·키보드만) 동작해야 한다 — 실제 기기(핸드헬드)에서 돌리니까.
- 값은 `Tuning` 구조체 **하나**(필드마다 이름·현재값·범위·단계). 코드는 `tuning.rs`의 기본값을 복사해 시작하고, 랩이 바꾸는 건 그 복사본이다. 내보내기는 `pub const NAME: f32 = 값;` 줄 — 사람이 붙여 넣고 커밋한다(저장 파일을 게임이 읽게 하면 "어느 값이 진짜인가"가 둘이 된다).
- 랩마다 **시나리오**가 딸린다: Camera Lab = 보스 하나 + 기둥 몇 개, Movement Lab = 빈 방 + 표지판, Combat Lab = 허수아비. 랩 화면에서 시나리오를 바꾸는 키 하나.
- 비교: 프리셋 A/B를 한 키로 번갈아 적용한다. 손맛은 "둘 중 어느 쪽"이 "이 값이 맞나"보다 훨씬 쉽게 답이 나온다.
- 우선순위: 카메라·이동(모든 것의 바탕) → 회피 → 공격(선딜·판정·후딜·히트스톱) → 적(수·속도·예고 시간) → 성능(적 수 vs 프레임 시간).
- Hecker의 사다리로 보면 "슬라이더 편집기 + 데이터 내보내기"가 1인 개발의 적정선이다. 핫 로딩(파일 감시)은 웹 빌드에서 안 되고, 스크립트 언어는 유지비가 크다.

### Game — 통과한 것만
- PoC 통과 + Lab 프리셋 확정 → `tuning.rs`에 값, 결정 기록에 "왜 이 값"과 판정한 날짜·사람.
- 실험용 화면은 cargo feature(`dev`, 기본 켬)로 가리고 운영판은 `--no-default-features`([운영판과 개발판](dev-and-release-flavors.md)).
- 프로토타입 단계에서는 배포본에도 랩을 켜 두는 편이 테스터에게 유리하다 — 테스터가 값을 만지고 "이게 좋다"를 보내 준다.

### 무엇을 랩에 두고 무엇을 두지 않나
- 둔다: 시간·거리·각도·배율처럼 **연속값**이고 느껴야 아는 것.
- 두지 않는다: 켜고 끄는 메커닉(그건 시나리오·결정의 몫), 이야기, 밸런스 표의 수백 칸(그건 표 파일을 고치는 게 빠르다).

## 왜?
손맛은 측정이 아니라 판정이고, 판정의 비용은 **같은 상황을 다시 만드는 시간 × 시도 횟수**다. 시나리오 진입점이 "다시 만드는 시간"을 초 단위로, 랩 슬라이더가 "시도 한 번"을 빌드 없이 만든다. 둘을 합치면 하루에 수백 번 시도가 되고, 그래야 "0.32초가 0.25초보다 낫다"를 느낌이 아니라 반복으로 정할 수 있다. PoC에 시간 상한을 두는 이유는 첫 게임에서 본 그대로다: 장기 프로젝트는 시간이 없어서가 아니라 **핵심 리스크를 콘텐츠가 쌓인 뒤에 발견해서** 죽는다.

## 함정
- 랩 값이 저장 파일에 남아 게임이 그걸 읽으면 "코드의 값 vs 파일의 값" 둘이 된다. 내보내기는 텍스트, 적용은 커밋.
- 랩을 마우스로 만들면 핸드헬드에서 못 쓴다. 패드 십자키 + 어깨 버튼으로.
- PoC 통과 기준을 뒤에 적으면 통과한 것처럼 보인다. 기준은 코드보다 먼저.
- 랩이 많아지면 그 자체가 유지비다. 값이 정해진 랩은 지우거나 시나리오 하나로 줄인다.
