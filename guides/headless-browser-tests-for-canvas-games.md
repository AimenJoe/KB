  1차(직접 실행·잼, 2026-11-27, nail-under-the-roots 0307 — macroquad 0.4 웹 빌드, Playwright 1.63 `page.clock`, 2D 320×180 게임):
  - **`clock.install`은 시계를 멈추지 않는다**: install 뒤 실제 0.5초를 기다리니 가짜 시각도 0.5초 흘렀고, `pauseAt` 뒤에는 0, `runFor(1000)`은
    정확히 1000을 더했다(빈 페이지에서 `performance.now()`·`Date.now()`로 잼). 같은 스크립트를 두 번 돌린 게임 시각은 124ms 달랐다.
  - install만 했을 때 같은 빌드 두 번의 차이: 창 화면 0.2~0.7%, 전경 2~6%, 걸어가서 연 창 30~40%. `pauseAt`을 넣자 한국어 33장이 다섯 번 넘게 0.
  - **키가 늦게 닿는다**: `page.keyboard`로 넣은 키와 `clock.runFor`는 순서가 보장되지 않았다 — 스크립트 둘을 겹쳐 돌려 기계를 바쁘게 하니
    걷다 멈춘 자리가 실행마다 달랐다. 키를 페이지 안에서 `window.dispatchEvent(new KeyboardEvent(…))`로 쏘자 걷는 구간이 여섯 번 다 같았고,
    가끔 깜빡이던 두 장(6px·48px)도 사라졌다. (게임 쪽이 창의 키 이벤트를 받아 넘기는 구조일 때 — nail `web/nail-host.js`.)
  - 로딩 프레임 수: 한 프레임을 흘리기 전에 받는 중인 요청이 끝나기를 기다리자 열두 번 모두 60프레임(그 전에는 실행마다 달랐다).
  - **짐작했다가 재 보니 아닌 것**(하나만 바꿔 여섯 번씩 돌림): 난수 씨앗 고정, 들어서며 나오는 대화를 없애기, 시계를 건너뛰기 전에 실제 시간
    더 주기, 소리 풀기(`decodeAudioData`)가 끝나기를 기다리기 — 넷 다 아래 "못 찾은 것"을 없애지 못했다.
    이 노트의 앞선 판이 "난수의 자리"·"한마디를 난수로 골라서"라고 적은 것은 **둘 다 틀렸다**(그 게임의 한마디 고르기에는 난수가 없다 — 코드를 읽고 확인).
  - 게임이 뜬 뒤에 시계를 걸면 게임 장면의 월드만 검게 찍혔다(메뉴 창은 멀쩡) — 열기 전에 걸자 사라졌다.
  - macroquad `get_time()`은 소스에서 `date::now() − start_time`임을 확인.
  - 못 찾은 것: 여섯 번에 한 번쯤 **한 번의 실행이 통째로**(두 언어 다, 첫 장부터) 한두 프레임 어긋난 갈래로 나온다 — 움직이는 것의 단계만 조금
    다르다. 처음에는 "독일어 로케일만 두 갈래"로 보였는데 도구를 고친 뒤 재니 언어가 아니라 실행 단위였다. 같은 갈래끼리는 66장이 픽셀까지 같다.
    (여섯 번 × 몇 묶음을 잰 것이라 비율은 어림이다.)
  확인 못 함: 다른 엔진(Bevy·Godot 웹)의 같은 함정. GPU가 있는 러너(유료)에서의 차이. 고친 파이프라인의 실제 CI 시간(첫 실행 뒤 적는다).

# 캔버스 게임의 헤드리스 브라우저 시험

## 요약
캔버스 하나뿐인 게임은 DOM 단서가 적어 `waitForTimeout`에 기대기 쉽고, 그것이 느린 CI 러너에서만 깨진다. **보이는 상태를 기다린다**:
DOM(로딩 덮개가 사라짐), 저장소(기록에 적힘), 게임 루프(rAF 두 번), 첫 프레임 신호. 재현은 CDP CPU 스로틀로 한다.

## 본문
1. **게임이 신호를 남기게**: 첫 프레임 뒤 로딩 덮개를 지운다(`#load` 요소 제거), 장면이 끝나면 기록을 쓴다. 시험은 `page.waitForFunction(() => !document.getElementById('load'))`,
   `waitForFunction(() => localStorage.getItem(k)?.includes('woke=1'))`처럼 그것을 기다린다.
2. **키 하나 = 게임 프레임 둘**: 엔진이 "한 프레임에 눌린 키 집합"으로 읽으면 빠른 연타가 한 번이 된다.
   `await page.keyboard.press(k); await page.evaluate(() => new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r))));`
3. **느린 기계를 흉내**: `const cdp = await ctx.newCDPSession(page); await cdp.send('Emulation.setCPUThrottlingRate', { rate: 5 });` —
   CI에서만 나던 실패가 로컬에서 몇 번에 한 번꼴로 난다. 고친 뒤 5배·8배에서 다시 돈다.
4. **저장을 심을 때**는 게임이 도는 탭이 아니라 같은 출처의 빈 페이지에서(게임이 끝날 때 제 기록으로 덮는다) 심고 다시 연다.
5. **겹치는 안내의 z 순서**도 시험이 본다: "안내가 보인다"는 요소가 있다가 아니라 맨 위에 있다(`elementFromPoint`).
6. **push 전에 CI가 돌리는 스크립트를 다 돌린다**: 메뉴 줄·탭 차례를 바꾸면 스크립트의 메뉴 길이 어긋난다. 바꾼 화면만 보는 스크립트로는 못 잡는다.
7. 고정 대기를 남겨야 하면(애니메이션을 찍는 사이 등) 그 값이 "판정"에 쓰이지 않게 — 스크린숏 간격은 되지만 "이만큼 기다리면 됐겠지"는 안 된다.

## 속도 — 헤드리스의 3D는 화소 수가 곧 시간
헤드리스 Chromium에는 GPU가 없어 WebGL을 CPU(SwiftShader)로 그린다. 그래서 시험 시간은 "기다린 시간"이 아니라 **그린 화소 수 × 프레임 수**다.
1. **먼저 잰다**: 단계별 시간(CI 로그의 타임스탬프)과 스크립트의 고정 대기 합을 견준다. 대기 합이 작으면 프레임이 병목이다 —
   `requestAnimationFrame`을 몇 초 세어 fps를 본다(1280×720에서 3 fps면 누름 하나가 0.7초).
2. **흐름만 보는 스크립트는 싸게 그린다**: 화면(뷰포트)을 줄이면 UI 배치·터치 자리가 바뀌니, 게임에 시험 깃발을 두어 **3D 타깃의 해상도만** 내린다
   (내부 해상도·슈퍼샘플링 끔). 그림을 사람이 보는 스크립트만 제 화질로 남긴다. 깃발은 개발 빌드에만.
3. **나란히 돌릴 때는 기계를 나눈다**: 소프트웨어 GL은 코어를 다 쓴다 — 한 기계에서 스크립트 둘을 겹치면 둘 다 느려지고, 시간으로 기다리는 곳이 깨진다.
   CI는 스크립트마다 잡(= VM)을 나누고(빌드 산출물은 아티팩트로 넘긴다), 필수 검사 이름을 지키려면 끝에 문지기 잡 하나가 앞 잡들의 결과를 본다
   (`if: !cancelled()` — 건너뛴 필수 검사는 통과로 읽힌다). 로컬에서는 차례로.
4. **배포 갈래에서는 나가는 것을 띄운다**: 개발 기능이 든 빌드로만 연기 시험을 돌면 실제 배포물(개발 기능을 뺀 빌드)은 한 번도 안 뜬 채 나간다.
   배포 직전에는 그 빌드를 타이틀까지 띄우고 "개발 메뉴가 없다"까지 보는 짧은 스크립트 하나면 된다 — 긴 시나리오는 PR 검사의 몫.
Rust 쪽(캐시가 맞으면 fmt·clippy·test·wasm 합쳐 2분)을 sccache·nextest로 더 줄이는 것은 이 경우 병목이 아니었다.

## 화면을 앞뒤로 견주려면 — 가짜 시계를 **멈춰야** 같은 그림이 나온다
리팩터링 앞뒤 스크린숏을 픽셀로 견주려면 같은 빌드가 같은 그림을 내야 한다. nail 0307에서 한 것(1·3이 재서 확인한 원인이고 1이 훨씬 크다):
1. **`page.clock.install()` 다음에 `pauseAt()`** — install은 시계를 가짜로 바꿀 뿐 **멈추지 않는다**(실제 시간과 함께 흐르고 `runFor`가 그 위에 더한다).
   멈추지 않으면 스크립트가 걸린 실제 시간만큼 게임 시각이 달라져 입자·몸짓뿐 아니라 걷는 거리까지 달라진다.
   둘 다 **페이지를 열기 전에**: 게임이 뜬 뒤에 걸면 게임이 보는 시각이 한 번 뛰어 보간으로 그리는 장면이 검게 찍힌다.
   ```js
   await page.clock.install({ time: T0 });
   await page.clock.pauseAt(new Date(T0.getTime() + 1000));   // 이제 runFor로 흘린 만큼만 흐른다
   await page.goto(url);
   ```
2. **로딩은 한 프레임씩 흘리며 기다리고, 가짜 시각을 정한 값까지 맞춘다** — 에셋 읽기는 프레임이 돌아야 진행되고 몇 프레임이 걸릴지는
   실행마다 다르다(네트워크·컴파일은 실제 시간). 인트로가 저절로 끝난 뒤의 시각으로 맞추면 그 뒤가 같다.
3. **키는 페이지 안에서 쏜다** — `page.keyboard.down`은 브라우저의 입력 길로 가고 `clock.runFor`는 페이지로 곧장 가서, 기계가 바쁘면 키가
   한두 프레임 늦게 닿는다(걷는 거리가 달라진다). 게임이 창의 키 이벤트를 듣는다면 `page.evaluate`로 `KeyboardEvent`를 `dispatchEvent` 한다 —
   `evaluate`가 돌아왔을 때는 이미 처리된 뒤다. (`isTrusted`를 보는 코드에는 안 통한다.)
   ```js
   const key = (type, code) => page.evaluate(([t, c]) =>
     window.dispatchEvent(new KeyboardEvent(t, { code: c, key: c, bubbles: true, cancelable: true })), [type, code]);
   ```
4. **한 프레임을 흘리기 전에 받는 중인 요청이 끝나기를 기다린다** — 로딩이 몇 프레임 걸리는지가 실제 시간에 기대지 않게
   (`page.on('request'/'requestfinished'/'requestfailed')`로 세어 0이 될 때까지).
5. **찍기 전에 실제 시간으로 잠깐**(Node 쪽 80ms) — 마지막으로 그린 프레임이 화면에 오른 뒤에 찍는다(넣었지만 따로 재지는 않았다).
6. 시험용 진입점은 **스스로 상황을 만들고**(기록을 꾸미고, 난수 씨앗을 정하고, 들어설 때 저절로 나오는 대화가 없게) 시작한다 — 이것들은
   잡음의 원인이 아니었지만(재 보니 그대로였다) 스크립트가 짧아지고 사람이 같은 상황을 바로 볼 수 있다.

그러고도 남는 것은 적어 둔다. nail에서는 여섯 번에 한 번쯤 실행 하나가 통째로 한두 프레임 어긋났다(원인 못 찾음). 쓰는 법은 단순하다:
**앞뒤를 견줘 모든 장이 조금씩 다르면 그 실행이 다른 갈래다 — 한 번 더 찍는다.** 진짜 변화는 몇 장에만, 정해진 자리에 나온다.

**짐작한 원인을 노트에 적을 때는 그것만 바꿔 여러 번 돌려 보고 적는다.** 이 절은 두 번 틀렸다: "난수의 자리 탓", 그다음 "들어설 때 한마디를
난수로 골라서". 둘 다 그럴듯했고, 둘 다 하나만 바꿔 재 보니 아니었다. 한두 번 같게 나온 것도 증거가 아니다 — 여섯 번에 한 번 나오는 일은
세 번 돌려서는 절반 넘게 안 보인다.

보는 범위도 넓힌다: 창을 보기만 하는 장면뿐 아니라 **동작 뒤 화면**(사기·넣고 빼기·거절 한마디·장면이 끝난 뒤)까지 찍어 두면, 화면을 다시 짜는
리팩터링을 한 커밋으로 옮겨도 한 번에 견줄 수 있다(nail: 2언어 × 33장).

## 왜?
고정 대기는 "이 기계에서 이만큼이면 된다"는 가정이다. 러너는 기계마다·시간마다 빠르기가 달라, 가정이 깨지는 날에만 빨간불이 나고(운영 배포 날일 수도 있다)
재현이 어렵다. 상태를 기다리면 빠른 기계에선 빨리, 느린 기계에선 늦게 지나간다.

## 함정
- 첫 프레임 전 키는 버려진다 — 게임이 뜨기 전에 누른 키가 아무 일도 안 한 것처럼 보인다.
- 로컬에서 늘 통과하는 시험 = 안전하다가 아니다. 스로틀로 돌려 본다.
- 게임이 쓰는 저장소에 시험이 같은 탭에서 쓰면 게임이 덮는다.
- 로컬에서 시험을 겹쳐 돌리며 "CI보다 느리네"를 재면 틀린다 — 부하가 다른 측정은 서로 견주지 않는다(앞·뒤를 같은 부하에서).
- 싸게 그리는 깃발을 건 스크립트의 스크린숏은 판정용이 아니다(도트가 굵다). 제 화질로 볼 길(환경 변수)을 남긴다.
